# 判负性能验证

2026-10-02 在本机 Node.js v24.14.1、Intel Core i9-14900HX 上测量。每种局面先预热 3000 次，再单独测量 20000 次 `getGameResult`；测量期间客户端正在打包。

| 局面 | p95 | p99 | 观察到的最大值 |
| --- | ---: | ---: | ---: |
| 标准开局 | 0.0051 ms | 0.0087 ms | 0.9514 ms |
| 32 步中局 | 0.0034 ms | 0.0048 ms | 0.3028 ms |
| 标准开局推进后的重炮将死 | 0.0899 ms | 0.1912 ms | 0.5439 ms |
| 困毙 | 0.0088 ms | 0.0167 ms | 0.3382 ms |

这 80000 个样本中最大值不足 1 ms，低于 60 Hz 界面的一帧时长（约 16.7 ms）。结果是当前机器上的实测数据，不包含网络延迟、页面绘制，也不保证所有电脑在任意系统负载下具有相同耗时。可执行 `npm run benchmark` 在另一台电脑上复测；脚本包含可重现的棋局。

## 算法上界与界面响应

不搜索多步游戏树。固定棋盘只有 90 个点，每方至多 16 子。按真实几何生成候选，每子最多 17 个直线目标，其他棋子更少；对每个候选用现有单步校验检查己方将帅安全，找到第一着合法应对立即返回。无合法着时最多检查 16 × 17 个候选，而不是按后续游戏深度指数展开。将帅安全检查扫描有限棋盘并按路径长度检查阻挡。

联机胜负判定在服务器执行，网页落子只校验当前一步。周期时钟消息仅刷新剩余时间文字，不触发判负、走法计算或棋盘重绘，因此不干扰拿起棋子和更换选择。

功能测试用暴力逐格校验作为独立对照：在特殊阻挡、炮架、过河、飞将、将军、双方镜像局面和对局抽样中，优化后的合法落点与逐个检查 90 点的结果一致。性能优化不会跳过其他棋子的救应走法。

## 吃子提示

v0.3.0 的提示同样只枚举敌方当前的合法直接捕获，不搜索后续棋树。结果按棋盘对象和己方阵营缓存；拿起、更换选择、翻转棋盘以及切换皮肤复用结果。时钟更新不调用分析或棋盘渲染。

2026-10-02 在相同 Node v24.14.1 / i9-14900HX 环境中，分别测试上述四类局面的原局、纵向镜像并换色、红方和黑方，共 16 组，每组预热 1000 次并采样 10000 次。下表为每类四组中的最差结果，仅包含 `dangerousPieces` 计算。
